# ADR-002: Factory + Strategy para seleccion de procesador

## Estado

Aceptado - 2026-05-19

## Contexto

El sistema maneja tres tipos de pedido: estandar, express e internacional. Cada uno tiene una forma distinta de calcular o describir el procesamiento. Una solucion basada en condicionales dentro de la fachada concentraria todas las variaciones en una sola clase y obligaria a modificarla cada vez que aparezca un nuevo tipo de pedido.

Ese enfoque afecta el principio abierto/cerrado porque una nueva variante no se agregaria extendiendo el sistema, sino editando la logica existente. Tambien haria mas dificil probar cada algoritmo por separado.

## Decision

Se usa el patron Strategy mediante el puerto `ProcesadorPedido`. Cada tipo de pedido tiene una implementacion concreta en `adaptadores.procesadores`: `ProcesadorPedidoEstandar`, `ProcesadorPedidoExpress` y `ProcesadorPedidoInternacional`.

La fachada recibe una lista de procesadores y construye un mapa por `TipoPedido`, funcionando como una factory en tiempo de ejecucion para seleccionar la estrategia correcta. De esta manera, la fachada no necesita conocer los detalles internos de cada algoritmo.

La decision se protege con una regla ArchUnit que exige que todas las clases del paquete `adaptadores.procesadores` implementen `ProcesadorPedido`.

## Consecuencias

Positivas:

- Agregar un nuevo tipo de pedido requiere agregar una nueva clase de procesador.
- Cada procesador puede probarse de forma independiente.
- La fachada conserva una responsabilidad clara: coordinar el caso de uso y delegar el calculo.

Negativas:

- Hay mas clases que en una solucion con un `switch`.
- Si dos procesadores declaran el mismo `TipoPedido`, el ultimo podria reemplazar al anterior en el mapa.
- La seleccion por mapa exige revisar las implementaciones disponibles para entender completamente que tipos estan soportados.
