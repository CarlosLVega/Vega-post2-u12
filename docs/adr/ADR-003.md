# ADR-003: Spring Events como Observer para notificaciones

## Estado

Aceptado - 2026-05-19

## Contexto

Cuando un pedido es procesado, el sistema debe permitir notificaciones posteriores como email, logs o futuros canales. Si la fachada llamara directamente a cada canal, la clase central del caso de uso quedaria acoplada a detalles secundarios y tendria que modificarse cada vez que se agregue una nueva notificacion.

El proyecto necesita una forma de publicar que algo ocurrio sin que el caso de uso conozca todos los receptores posibles.

## Decision

Se modela el hecho de negocio con `PedidoProcesadoEvent` y se define el puerto `PublicadorEventos` en el dominio. La infraestructura implementa ese puerto con `PublicadorEventosSpring`, usando `ApplicationEventPublisher` como mecanismo tecnico.

Los receptores se implementan como listeners independientes. `NotificadorEmail` escucha el evento mediante `@EventListener`, representando el patron Observer: el publicador emite el evento y los observadores reaccionan sin que la fachada dependa directamente de ellos.

## Consecuencias

Positivas:

- Agregar un nuevo canal de notificacion no requiere modificar la fachada.
- Si no existe ningun listener, publicar el evento no rompe el flujo principal.
- Los eventos hacen explicito el momento relevante del dominio: un pedido fue procesado.

Negativas:

- El flujo posterior al procesamiento es menos visible que una llamada directa.
- El orden de ejecucion entre listeners no debe asumirse salvo que se configure explicitamente.
- El diagnostico de errores puede requerir revisar varios listeners para entender todas las reacciones al evento.
